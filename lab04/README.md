### 2. Теоретичний аналіз CPython: Стек та TCO

#### Чому в CPython немає TCO (Tail-Call Optimization)?[cite: 15]
Гвідо ван Россум свідомо відмовився від TCO в інтерпретаторі з таких міркувань:
1. **Збереження інформації трасування (Stack Traces):** оптимізація хвостового виклику перезаписує поточний фрейм стеку новим викликом. У разі виникнення винятку стек викликів був би неповним, що суттєво ускладнює відлагодження програми.
2. **Динамічна природа Python:** у Python функції та змінні локальної області видимості можуть модифікуватися динамічно в рантаймі. Перевірка придатності виклику до TCO на кожному кроці сповільнювала б звичайне виконання.

#### Ліміт стека викликів:
- Стандартне обмеження глибини стеку в CPython становить 1000 викликів (`sys.getrecursionlimit()`)[cite: 15].
- При перевищенні ліміту Python генерує виняток `RecursionError`[cite: 15].
- **Висновок:** для глибоких графів, великих лабіринтів або дерев довільного розміру слід переходити на **ітеративні структури** (з власним стеком або чергою в купі пам'яті)[cite: 15].

### 3. Огляд алгоритмів лабіринту (Варіант №9):
- **Рекурсивний DFS:** елегантна реалізація без побічних ефектів; стан відвіданих вершин передається як `frozenset`, результат конструюється додаванням кортежів[cite: 15].
- **Ітеративний DFS:** зберігає шлях на власному стеку списку Python[cite: 15]. Працює за межами ліміту стека інтерпретатора[cite: 15].
- **Ітеративний BFS:** на відміну від DFS, гарантує знаходження **найкоротшого шляху** за рахунок хвильового розгортання черги `deque`[cite: 15].
- **Мемоізація `make_path_counter`:** обчислює кількість маршрутів на сітці з перешкодами за допомогою `@lru_cache`, демонструючи перехід від експоненційної складності $O(2^{R+C})$ до поліноміальної $O(R \times C)$[cite: 15].
